## Layout

```
Reaper/                     mirrors REAPER's resource path; this is what gets installed
  Scripts/MXM_ListOfInstrumentsAndEffects/
    MXM_List of Instruments and Effects.lua    the window
    lib/scan.lua                               walks the project's FX chains
    lib/report.lua                             renders the four export formats
    lib/theme.lua                              corners, padding, colours
    lib/about.lua                              name, version, links, licence
    lib/chunk.lua                              reads offline containers out of
                                               the project state
  Data/toolbar_icons/       the toolbar icon, at 1x, 150 and 200
ReaPack/                    the ReaPack manifest, and nothing else
tests/                      headless suites for lib/
docs/                       this site; src/assets/ holds the screenshot
icon/                       icon.svg, the master every icon output is rendered from
images/                     a frozen copy of the screenshot, kept only so the URL in
                            the already-published index keeps resolving; delete once
                            the combined index has caught up
index.xml                   generated by reapack-index; never edit by hand
CHANGELOG.md                release notes; the GitHub release body comes from here
.github/scripts/package.py  validates the manifest and builds the manual-install zip
```

The package is listed under **Various**, but that is not where the manifest
lives. `reapack-index` takes the category from the manifest's directory, so this
repository's own `index.xml` lists it under `ReaPack`. `merge-index.py`, in the
ReaPack repository, renames that to the category configured for each source
when it builds the combined index users import. Every script keeps its manifest
at `ReaPack/` that way, whatever its category. The `@provides` lines retarget
with `../`, so no category is part of the install path.

Do not rename the manifest file, or change the category configured in
`merge-index.py`: ReaPack's package identity is (index, category, package), and
changing any of the three orphans every existing install.

## Tests

`lib/scan.lua` and `lib/report.lua` touch neither REAPER nor ReaImGui, so they
run anywhere:

```bash
make test
```

`tests/mockreaper.lua` stands in for the ReaScript API. REAPER ships Lua 5.4.
`run.sh` prefers it when several are installed, and honours `LUA=/path/to/lua`.

## Icons

Edit `icon/icon.svg`, then:

```bash
make icon
```

This renders the README mark, the toolbar strips and the favicons. Commit what
changes.

## This site

```bash
make docs        # build, then serve it exactly as published
make docs-dev    # live-reload server, for writing
make docs-build  # static build into docs/dist/
```

`make` on its own lists every target.

GitHub Actions builds and deploys it on every push to `main` that touches
`docs/`.

## Releasing

Download URLs are locked to a git tag rather than a commit: `.reapack-index.conf`
sets `--url-template .../raw/v$version/$path`. `$version` expands to the
`@version` string exactly, so **the tag must be `v` plus that string**, and it
must sit on the commit carrying the files. Versions are `major.minor.patch`.

1. Bump `@version` and write the `@changelog` in
   `ReaPack/MXM_List of Instruments and Effects.lua`, and set `VERSION` in
   `lib/about.lua` to match. `tests/test_about.lua` fails if the two drift.
   Rename `## [Unreleased]` in `CHANGELOG.md` to `## [<version>] - <date>`.
   `make package-check` confirms the manifest provides every file under `Reaper/`.
2. Commit the payload and squash-merge the branch into `main`. Squash, because
   `reapack-index` walks every commit it can see — intermediate commits
   declaring a version that never shipped would each become a version of its own.
3. Tag that commit `v<version>` and **push the tag**.
4. Run `reapack-index` and commit `index.xml` on its own. (`--rebuild` is needed
   only when the URL template itself changes.)
5. Check the generated `<source>` URLs resolve. `reapack-index` never looks: a
   tag that does not exist yields a perfectly valid-looking entry that 404s when
   somebody installs it.
6. Re-merge the combined index in the `ReaPack` repository. Until that runs, the
   release reaches nobody.
7. Run *Actions → Release* on GitHub with the tag. It checks the tag against
   `@version`, runs the tests, zips what `@provides` lists (`make package` builds
   the same zip locally), and publishes a GitHub release with the zip attached
   and the version's `CHANGELOG.md` section as its description.
